# Contributing

Thanks for looking. Traces started as a hackathon project, so the codebase is small and the
conventions are few — but the few there are exist for reasons, and this document is where they're
written down.

Two neighbours to this file: [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) covers participation, including
the one project-specific clause about publishing recordings of real people, and
[SECURITY.md](SECURITY.md) is where a vulnerability goes instead of into a public issue.

---

## Getting set up

```bash
git clone https://github.com/ribdsp/Traces.git
cd Traces

cd traces && npm install && npm run dev        # the app          → localhost:3000
cd ../bugbait && npm install && npm run dev    # the broken demo  → localhost:3001
```

Two terminals: both dev servers run at once, and the app is not much use without a recording to load.

To exercise the tool surface you need WebMCP available in the browser. Three options, in descending
order of fidelity:

1. **Chrome 149+ or Edge 150+ with an origin trial token** for your origin. Closest to what real
   users get.
2. **The WebMCP polyfill** (`traces/src/lib/webmcp/polyfill.ts`), which loads automatically in
   development. Good enough for building; not good enough for judging whether a schema is legible to
   a model.
3. **The `webmcp-tools` browser extension**, which gives you an inspector over the registered tools.
   Use this to call tools by hand.

You don't need a real agent for most work. You do need one before claiming a tool works — see
[Testing a tool](#testing-a-tool).

`traces/` and `bugbait/` install separately — neither is a workspace member, and there is no lockfile at
the repo root. `npm ci` works in both, and `npm audit` reports zero vulnerabilities in both; if either
stops being true, that's a change to fix rather than to note. Two entries in those manifests exist for
reasons JSON has no room to state:

- **`overrides: { "postcss": "^8.5.26" }`** in both. The advisory is against a copy of postcss nested
  under `next`, not the one either app depends on directly, so bumping the direct dependency does
  nothing. The alternative `npm audit fix --force` offers is a Next major, which is a much larger change
  than the one-line fix the advisory actually needs.
- **`vitest` on 4.x**, not the 2.x this was built against. Two advisories, one of them critical, are
  fixed only in 4.x. The suite needed no changes — but the config had to become `vitest.config.mts`,
  since `.ts` in a package without `"type": "module"` is loaded as CommonJS and Vite's native config
  loader is about to stop tolerating that.

## Three rules that aren't negotiable

These come from the [threat model](docs/threat-model.md). A PR that breaks one will be rejected even
if everything else about it is good.

### 1. Nothing from the model is ever executed

No `eval`, no `new Function`, no dynamic `import()` of a model-supplied string, no
`setTimeout("string")`. Predicates are a closed set of structured objects — if you need a new kind of
predicate, **add a variant with its own evaluator**; don't add an escape hatch.

There is a test that greps the source for `eval(` and `new Function` and fails the build. If you find
yourself wanting to suppress it, that's the signal to stop and open an issue instead.

### 2. Every tool response has a budget

Compressed DOM: 60 lines, 1,200 characters. `list_events`: 40 entries. `diff_dom`: 30.
`find_element`: 5 matches. Console messages: 200 characters each.

New tools need a budget too. Pick one, enforce it in the response, set a `truncated` flag, and tell
the agent what to do about it (`"narrow the scope"`) rather than only reporting that something was
cut. Agents act on instructions much more reliably than on observations.

Context-window exhaustion is a *silent* failure: the agent keeps answering, just worse. Budgets are
the only defence, and unenforced budgets erode within a week.

### 3. No real user recordings in this repository

Every recording in `traces/public/recordings/` is synthetic, generated by `bugbait/`. Session
recordings of real people contain whatever those people typed — names, addresses, order contents.

`.gitignore` blocks `*.session.json` outside the samples directory, but the rule matters more than the
mechanism: if you point Traces at your own product and get a useful recording, keep it out of version
control.

## Code conventions

- **TypeScript strict.** No `any` in `lib/`. If a type is genuinely unknown, `unknown` plus a
  narrowing function.
- **JSON keys are camelCase**, in tool responses and everywhere else.
- **File names are kebab-case.** `compress-dom.ts`, not `compressDom.ts`.
- **`lib/` is pure.** `lib/replay`, `lib/dom`, and `lib/bisect` take data and return data. They don't
  import React, don't touch the store, and don't know WebMCP exists. This is what makes them testable
  without a browser — please don't erode it for convenience.
- **Every state mutation goes through an action, and every action carries `author`.** No direct
  `setState` from components. The activity feed's correctness depends entirely on this, including for
  code written by people who never read this file.
- **Actions return new objects.** Per-contribution undo needs previous states intact.
- **Small files.** 200–400 lines is normal; past 800, split.

## Testing policy

Deliberately uneven, and worth explaining rather than defending.

**Tested thoroughly:**

| Module | Why |
|---|---|
| `compress-dom` | budget violations are silent — the agent keeps working, just worse |
| `predicate` | it's the security boundary |
| `bisect` | an off-by-one produces a *confidently wrong* timestamp, which is worse than an error |
| `build-report` | it's what stops fabricated reproduction steps reaching a human |
| the no-`eval` grep | prevents quiet regression under time pressure |

**Not covered by automated tests:** UI components, the rrweb integration, end-to-end flows.

The reasoning: bugs in the four modules above fail *invisibly* — you get a plausible answer that's
wrong. Bugs in the UI announce themselves within five seconds of opening the page. The test budget
goes where failures hide, not where they're loud.

```bash
cd traces && npm test
```

If you add anything to `lib/dom`, `lib/bisect`, or `lib/report`, it needs tests. UI is fine without.

## Testing a tool

A tool that works when you call it from your own code can still be unusable, because the failure mode
is a schema a model consistently misreads. Before saying a tool works:

1. Call it from the `webmcp-tools` inspector with arguments you type by hand.
2. Call it from a real agent, with a task phrased the way a user would phrase it — not with
   arguments you already know are correct.
3. Check that failures come back as **readable tool errors**, not thrown exceptions. Good:
   `Unsupported predicate kind 'jsExpression'. Supported: propertyEquals, attributeExists, ...`
   An agent given that sentence corrects itself on the next call.

Tool `description` fields are part of the interface. A tool whose description doesn't explain *when*
to use it will be used at the wrong moment. `ask_human_visual` in particular has to state that the
agent cannot see rendered output, or models reach for it as a general-purpose escape from
uncertainty.

## UI conventions

Traces is an instrument for engineers, not a landing page: **dense, quiet, scannable.** High
information density in the timeline. No decorative gradients, no oversized rounded cards, no
marketing voice in an ops tool.

Empty, loading, and error states are all three required, not just the one you happened to hit while
developing.

### The type scale has a floor, and the floor is 13px

Ask for a role, not a size: `text-micro` `text-label` `text-meta` `text-body` `text-title`, defined in
`tailwind.config.ts`. Never write `text-[11px]` in a component — a hundred hardcoded sizes cannot be
raised together, and this scale has already had to move once.

| Token | Size | For |
|---|---|---|
| `text-micro` | 10px | A glyph and nothing else: a `kbd` key cap, a timeline tick label, an ordinal. Never a phrase. |
| `text-label` | 11px | Uppercase section labels, status chips, author badges, counts. |
| `text-meta` | 12px | Mono metadata, secondary notes. |
| `text-body` | 13px | **The floor for any sentence a person has to read.** |
| `text-title` | 15px | The wordmark, and a title that has to win against the body under it. |

Why a floor at all: this app is demonstrated through a screen recording, and a compressed 1080p frame
scaled into someone else's player turns 10px body copy into grey texture. Density comes from padding
and line-height, which cost nothing on video; it does not come from shrinking the words.

### Radius stops at 6px, and depth is never a shadow

`rounded-sm` (3px) for controls and chips, `rounded-md` (6px) for panels, `rounded-full` for dots
only. Larger values are not in the theme, so `rounded-lg` and friends do not resolve — the scale is
*replaced* rather than extended, which turns "no oversized rounded cards" above from a request into a
build error.

`boxShadow` is replaced the same way and holds only `shadow-panel` / `shadow-raised`, both inset top
highlights. A raised surface is lit along its top edge and paired with `border-line-strong`; nothing
in an instrument floats above the chassis.

### Focus is global, so do not suppress it

`globals.css` puts a 2px `ink` outline on `:focus-visible` for every element at once. Do not add
`focus-visible:outline-none` to get a custom treatment — change the background alongside the ring if
you want more, but every interactive element keeps a visible focus state, and every dropdown and
disclosure stays keyboard-operable.

### Motion is for four things

A blocking gate waiting, a claimed task working, the bisect probe sequence arriving, a recording
loading. Nothing else moves — no page-load animation, no scroll effect, no hover lift.

Under `prefers-reduced-motion` `globals.css` caps `animation-iteration-count` at 1, which lands every
`animate-pulse` on its last keyframe — `opacity: 1`, a solid dot. Note *which* declaration does that
work: zeroing `animation-duration` alone, which is the usual reset and was what this file used to
claim, does not stop an `infinite` animation at all — it runs the same cycle a hundred thousand times a
second. So **any state signalled by movement must also be legible standing still**: two icons rather
than one rotated, a word beside the dot, a colour that stays. `webmcp-badge.tsx`'s chevron is the
reference for the pattern, and the dot may stop moving but must never disappear — in all four places it
is the thing saying something is still happening.

## Pull requests

- Branch off `main`, which stays deployable.
- Small and frequent beats large and complete.
- PRs touching `lib/dom`, `lib/bisect`, or `lib/webmcp` need a second reader — those are where bugs
  hide without announcing themselves. `components/` doesn't.
- Commit messages: `<type>: <description>` with types `feat`, `fix`, `refactor`, `docs`, `test`,
  `chore`, `perf`, `ci`.

## Adding a tool

The checklist, in order:

1. A pure function in `lib/` that does the actual work, with tests if it's in `dom`/`bisect`/`report`.
2. A thin wrapper in `lib/webmcp/tools/<name>.ts`.
3. A response budget.
4. A JSON Schema with a `description` on the tool **and on each non-obvious field**, plus an example.
5. Readable errors for every rejection path.
6. An entry in [docs/tools.md](docs/tools.md) — the contract is documentation, not just code.
7. Tested from the inspector *and* from a real agent.
